# SewTec CRM feature, access, and persistence matrix

This matrix describes the hardened local application. “Rep” means an active `rep` in the authenticated branch. “Admin” means an active `admin` in that same branch. There is no company-wide super-admin. The database query filters and write validation enforce these rules; hiding a frontend control is only an additional usability measure.

| Feature and visible action | HTTP operation and stored data | Rep access | Admin access | Acceptance evidence |
|---|---|---|---|---|
| Sign in | `POST /api/auth/login`; verifies the active account and issues a signed JWT carrying account ID, branch, role, and session version. No CRM record is written. | Own account | Own account | Login rate policy, invalid credentials, and revoked session are covered by HTTP integration tests. |
| Restore session / sign out | `GET /api/auth/me`; validates the current database account on every authenticated request. Logout clears the token and all in-memory CRM data in every tab. | Own account | Own account | Account password change revokes an existing token; browser journey verifies cross-tab logout. |
| Dashboard | Paged `GET /api/follow-ups`, `GET /api/opportunities`, and `GET /api/customers`; aggregated values are scoped in SQL. | Assigned customers and work only | Whole current branch | HTTP resource isolation tests and dashboard browser audit. |
| Global search | `GET /api/search?q=...`; searches scoped customers/opportunities plus the shared product catalog and caps each result group. | Assigned customer/work results; catalog results | Current branch; catalog results | Direct cross-user and cross-branch IDs remain absent; anonymous request is rejected. |
| Customer list, filters, and cards/table | `GET /api/customers?page=&pageSize=&search=&type=&assignedRepId=&isStale=`; returns `items`, `totalCount`, paging metadata, and scoped summary. | Assigned customers only | Current branch | Rep A, rep B, branch B, paging, empty result, stable ordering, and mobile widths exercised. |
| Create customer | `POST /api/customers`; writes `Customers` and one or two `CustomerPhones` identities in one transaction. Server derives branch and validates assignment. | Created customer is assigned to caller | May assign an eligible active branch user | Browser failed-save/retry and save/reload journey; simultaneous duplicate HTTP creates; Arabic/international phone formats. |
| Edit customer | `PUT /api/customers/{id}` with `If-Match`; updates the customer and denormalized related display fields in one transaction. | Assigned customer only | Current branch | Missing/stale revision tests, direct inaccessible ID tests, and browser edit/reload journey. |
| Duplicate phone handling | Unique `CustomerPhones.NormalizedPhone` primary key covers primary-to-primary, primary-to-secondary, and secondary-to-secondary matches company-wide. | Conflict response discloses an existing ID only if the record is visible | Same rule; no cross-branch disclosure | Equivalent `+20`, local, punctuation, and Arabic-digit forms plus concurrent creates are tested. |
| Installed machines | `POST /api/customers/{id}/machines`; writes `InstalledMachines`, validates model, quantity, year, and customer access. | Assigned customer only | Current branch | Browser journey verifies quantity two is stored once and survives a fresh API query. |
| Opportunity list and totals | `GET /api/opportunities` with server paging/filtering and SQL stage/value summary. | Assigned customers only | Current branch | Endpoint matrix isolation and paged data hooks. |
| Create/edit opportunity | `POST /api/opportunities`, `PUT /api/opportunities/{id}`; writes `Opportunities`, adjusts customer pipeline/lifetime totals, and records stage activity. | Assigned customer only; assignment fields are ignored in favor of customer ownership | Current branch | Balance reversal tests, forged owner tests, invalid quantity/value/date tests, and transaction middleware. |
| Change opportunity stage | `PATCH /api/opportunities/{id}/stage` or the edit operation; writes the new stage/revision, customer balances, quotation reference where needed, and `Activities`. | Assigned customer only | Current branch | Repeated identical stage is side-effect free; stale writes conflict. Mobile provides a tap action so dragging is optional. |
| Follow-up lists and date views | `GET /api/follow-ups` with paging and Cairo-day filters. | Assigned customers only | Current branch | Overdue/today/upcoming filters and Africa/Cairo boundary helpers are tested. |
| Create/reschedule follow-up | `POST /api/follow-ups`, `PATCH /api/follow-ups/{id}/reschedule`; writes `FollowUps`, revision, and recalculated customer `NextFollowUpAt`. | Assigned customer only | Current branch | Invalid dates, stale revisions, reload, and tap-based mobile date/time sheet. |
| Complete / no-answer follow-up | `POST /api/follow-ups/{id}/complete`; atomically updates the task and customer, creates `Interactions` and `Activities`, and optionally creates the next task. | Assigned customer only | Current branch | Forced invalid next task leaves no partial writes; repeat completion returns conflict; Cairo next-day retry is tested. |
| Interaction and quick note | `POST /api/interactions`; atomically writes interaction, activity, customer last contact, and optional next follow-up. Server stamps actor ID/name and customer facts. | Assigned customer only | Current branch | Forged actor/customer names are overridden; fresh activity and interaction counts are verified. |
| Customer history | `GET /api/activities/customer/{id}` and `GET /api/interactions/customer/{id}`. | Assigned customer only | Current branch | Direct inaccessible customer IDs return an empty scoped collection; browser refresh restores history from API. |
| Catalog browse, search, filter, sort | Paged `GET /api/products`; returns stable page and full-catalog summary. `GET /api/products/{id}` reads one product. | Authenticated | Authenticated | Paging has disjoint stable pages and total count; injection-shaped search is safe; mobile/desktop catalog surfaces audited. |
| Catalog create/edit/delete | `POST`, `PUT`, `DELETE /api/products`; writes `Products`. | Forbidden | Current branch admin role (catalog itself is shared) | Rep write attempt returns 403; negative prices and missing models are rejected. |
| Catalog and price file import | `POST /api/products/import-catalog` and `/import-prices`; bounded 5 MB upload, validation, transactional replacement/update. | Forbidden | Allowed | Invalid row/negative price tests leave existing products unchanged. Server-filesystem seed route is disabled. |
| Catalog CSV templates/export | `GET /api/products/templates/*` and `/export-csv`; reads catalog only. | Authenticated | Authenticated | Authenticated download path uses common session-expiry handling; anonymous requests are rejected. |
| User directory | `GET /api/users/directory`; active users are filtered by branch and role scope. | Caller’s own directory identity | Active users in current branch | Anonymous and cross-branch requests are covered. |
| User administration | `GET/POST/PUT/DELETE /api/users`; writes `AppUser`. Password/role/active changes rotate session version. | Forbidden | Current branch | Known-role and password rules, last-active-admin protection, cross-branch IDs, session revocation, and owned-work safeguards are tested. |
| Team monitoring | `GET /api/users/monitoring`; SQL grouping uses durable actor IDs and branch-scoped ownership. | Forbidden | Current branch | Rep receives 403; actor count survives a user rename. |
| Mentoring | `GET/POST /api/mentoring/notes` and `GET /api/mentoring/summary`; writes `MentoringNotes` with rep ID, author ID, branch, and server-derived names. | Forbidden | Current branch | Rep/admin IDs are validated in the branch; type and message validation are server enforced. |
| Branch/system information | `GET /api/system/info`; returns scoped counts, branch ID, timezone, database engine, and UTC server time. | Forbidden | Current branch | Cross-role test verifies 403; no filesystem path or whole-database size is exposed. |
| Demo reset and database download | `/api/demo/reset` and `/api/system/backup` deliberately return 404. | Unavailable | Unavailable | HTTP integration tests verify both routes. Migration, backup, restore, and reviewed merges are operator commands. |
| Health and readiness | `GET /health` reports process liveness. `GET /ready` requires database connectivity and no pending migrations. | Hosting probe | Hosting probe | Local final schema reached readiness; host probe behavior remains a deployment acceptance item. |

All customer-related global filters follow the relationship to `Customers`, so opportunities, follow-ups, interactions, activities, and installed machines cannot be exposed merely by guessing a child ID. Catalog data is intentionally shared among authenticated users. Company-wide phone collision detection is intentionally global but does not grant record visibility.
